Configuration files

oceanarray reads a few YAML files. Each says what is being processed, not where files are on a machine, so the same files work with any directory layout: the raw-data folder, the processed folder and the bathymetry file come from the call or the command line. Two keys of the mooring YAML still name a file relative to the YAML, sensor_catalog and caldip.root; both are planned to move to the call and the command line.

The package also ships tables of its own (config/logging.yaml, flag_meanings.yaml); they are not edited by users.

Finding a mooring

A mooring’s name is always its name: key: every file it produces is named from it. The name is never taken from the YAML’s file name or its folder; those only help find the file. oceanarray supports two ways of working, and both are kept working:

  • Your own directory structure, by path. Give the mooring YAML’s path (oceanarray run /data/configs/my_mooring.yaml --raw-dir /data/raw, or read_mooring(path); --raw-dir is needed whenever stage 1 runs). The file can have any name; on the command line the stage files are written in the folder that holds it, and in Python in the folders of a Paths (Where the folders are: paths.yaml).

  • The prescribed directory structure, by name. Keep each mooring’s files in {proc_dir}/{name}/, with its YAML as {name}.mooring.yaml; then the name alone is enough (oceanarray run M2_2016 --proc-dir proc). A folder holding exactly one *.mooring.yaml can also be given instead of the name.

An array YAML lists its moorings by name. Each is found as {name}.mooring.yaml beside the array file or in its processed folder; a mooring whose YAML is named differently gives that file name as config: (a file name only, no folders).

Where the folders are: paths.yaml

New in 0.7.0. A paths file states a project’s folders in one place, so a project shared between people and machines needs no folder options. Relative folders are relative to the paths file; ~ is expanded.

# paths.yaml
yaml_dir: config/moorings        # the *.mooring.yaml files
raw_dir: ~/data/raw-OSNAP        # raw files, one folder per mooring
proc_dir: ~/data/proc-OSNAP      # stage, stack and grid files, one folder per mooring
report_dir: outputs/report       # report pages, one folder per mooring
export_dir: outputs/export       # OceanSITES files
# caldip_dir: ~/data/caldip      # optional: caldip outputs

moorings:                        # optional: exact folders for a mooring that differs
  M2_2016:
    raw_dir: ~/data/raw-OSNAP/2018_recovery/M2

A mooring’s folder is <dir>/<mooring_name>; under moorings: it is the folder as written. The keys are exactly those above; any other key is an error. In Python:

import oceanarray as oa

paths = oa.Paths.from_file("paths.yaml")
paths.mooring_path("M2_2016")     # config/moorings/M2_2016.mooring.yaml
paths.raw_mooring_dir("M2_2016")  # the mooring's raw folder
paths.mooring_dir("M2_2016")      # its processed folder
paths.mooring_paths()             # every mooring YAML, sorted

# the standard structure under one folder: yamls/, raw/, proc/, reports/, exports/
paths = oa.Paths.standard("/data/OSNAP")

# or each folder given, and one mooring with its own raw folder
paths = oa.Paths(yaml_dir="config/moorings", raw_dir="/data/raw", proc_dir="/data/proc")
paths = paths.with_mooring("M2_2016", raw_dir="/media/usb/M2")

A mooring YAML still in its processed folder ({proc_dir}/{name}/) is found there, with a deprecation warning, until 0.8.0.

The verbs (run, process, report, export) take the mooring YAML’s path and a Paths, and take every folder from it:

mooring_path = paths.mooring_path("M2_2016")
oa.run(mooring_path, paths)               # stage files, stack and grid in paths.mooring_dir
oa.report(mooring_path, paths, pdf=True)  # pages and PDF in paths.report_mooring_dir
oa.export(mooring_path, paths)            # OceanSITES files in paths.export_dir

Coming next: the command line takes a paths file (--paths); until then it builds a Paths from --raw-dir, --proc-dir, --report-dir and -o.

Each mooring YAML stands alone

A mooring YAML holds every setting for its mooring, so one file is enough to reprocess it. Nothing is inherited at run time from the array YAML or any other file: a setting shared by several moorings is written into each mooring’s file.

The array YAML groups moorings that are already described. It decides what the year page shows and supplies site_code and project when the moorings are exported to OceanSITES; it never changes how a mooring is processed.

Subarrays

A subarray is a named group of moorings within an array (for example the Cape Farewell moorings of OSNAP East). It exists only in the array YAML, as a key of subarrays that each mooring entry may name, and is used only for display: the year page colors and groups moorings by subarray. There is no subarray file, and subarrays are not written into the data files.

Which value wins

A setting can come from four places. From lowest to highest priority:

  1. the package default (oceanarray.config.parameters);

  2. the mooring YAML;

  3. the instrument’s entry in the mooring YAML;

  4. the call (a keyword argument) or the command-line flag.

For example, the stack time step is 3600 s by default; stack: {dt_seconds: 1800} in a mooring YAML sets 1800 s for that mooring, and --dt-seconds 600 on the command line overrides both for that run.
