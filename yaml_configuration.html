The mooring YAML file

Each mooring is described by one YAML file, {mooring_name}.mooring.yaml. It holds everything oceanarray needs to process the mooring: what instruments were deployed and at what depths, when the mooring was in the water, and how to quality-control the data. It does not choose where files are: the raw-data folder and the processed folder are given when the pipeline is run (raw_dir / --raw-dir, see Files and folders). Two keys still name a file relative to this YAML, sensor_catalog and caldip.root; both are planned to move to the run. How this file relates to the other configuration files is on Configuration files.

Minimal working example

The following YAML is sufficient to process a mooring that carries one SeaBird microCAT and one Nortek Aquadopp. Copy it and fill in the values for your deployment before running any oceanarray command.

name: dsG3_1_2026
waterdepth: 1800
deployment_time: "2026-04-10T12:00:00"
recovery_time: "2027-04-15T08:30:00"

# Position — used for magnetic declination correction
deployment_latitude: "65 29.84 N"
deployment_longitude: "009 30.12 W"

clamp:
  - serial: "26261"
    instrument: microcat
    filename: 26261_recovery.asc
    file_type: sbe-ascii
    hab: 450
    computer_clock_at_recovery: "2027-04-15T08:00:00"
    instrument_clock_at_recovery: "2027-04-15T07:59:48"

  - serial: "400115"
    instrument: aquadopp
    filename: A400115_dsG3.aqd
    file_type: nortek-raw
    header_file: A400115_dsG3.hdr
    hab: 460

Instrument entries (the clamp list)

Each physical instrument on the mooring appears as one entry under the clamp key. Entries are processed in the order they appear; oceanarray does not re-order them by depth.

Instrument type. Controls the raw-file subdirectory, the output subdirectory, which processing code paths are activated, and the instrument-type column in reports. See The instrument field for the full list of valid values.

Per-instrument QC overrides. Same structure as the mooring-level blocks; instrument-level values override mooring-level values for the same variable.

OceanSITES data mode after a manual review: one letter for all the instrument’s variables, or {variable: letter}, with P (provisional, the default) or D (delayed mode). D is refused by the export unless the stage-3 file records the calibration-dip correction.

boolean

Set to true to skip this instrument entirely during processing. The entry is retained in the YAML for documentation purposes.

Free-text explanation for why the instrument is skipped. Displayed in reports alongside the skipped indicator, e.g. "pressure sensor failed at deployment".

string

Special sentinel value indicating no data file exists yet. Processing is skipped; the instrument appears in reports as pending.

boolean

Set to false to keep this instrument out of the stack and grid while still processing it through Stages 1–3 and its instrument report (reference data, e.g. a low-passed RODB .lowedt file). units_override

mapping

Corrects a file whose units attribute is wrong, as {variable: units}, e.g. {conductivity: mS/cm} for a file that labels mS/cm values S/m. Applied in Stage 1 before the units pass; the stated value is kept in the variable’s units_override_from attribute. For oceansites and rodb files Stage 1 checks each variable’s median against the registry’s valid range and refuses the instrument, naming this key, when the stated units look wrong. An entry can also be {units: <units>, reason: <text>}, e.g. {pressure: {units: kPa, reason: "ERDDAP labels decibars; values are ten times the deployed depth"}}; the reason is kept in the variable’s units_override_reason attribute. When the corrected units are not the canonical ones (kPa for pressure), the units pass converts the values and records units_converted_from and units_conversion_factor.

sensor_model, sensor_model_source

string

The instrument’s model (SBE 37-SMP) and where it came from (required with the model). Fills the sensor record’s sensor_model when the file names none, and replaces a file’s model with a warning (the file’s stays as originator_sensor_model).

Additional fields

sample_interval_seconds

Nominal sampling interval in seconds. Used by oceanarray in HTML reports (shown in instrument metadata cards and compared against the actual computed sampling interval) and by moordiag for the mooring diagram. Does not affect any data processing.

label

Short human-readable name for the instrument, e.g. "SM-p" or "Aquadopp". Used by moordiag for diagram labels and may be used by oceanarray as a legend label in plots.

clamp_id

The clamp position on the mooring line. Used by moordiag; oceanarray records it on each instrument’s files (the clamp_id attribute).

Fields used only by moordiag (ignored by oceanarray)

The following fields are read by the moordiag mooring diagram package and are ignored by oceanarray: image, position, hardware_type, category, component_id, length, repeat. They may safely remain in the YAML alongside the processing fields.

The instrument field

The instrument field in each clamp entry does four things:

  1. Raw-file subdirectory: oceanarray looks for raw files in {raw_dir}/{mooring}/{instrument}/.

  2. Output subdirectory: stage NC files are written to {proc_dir}/{mooring}/{instrument}/.

  3. Processing code path: the value activates instrument-specific processing. For example, aquadopp triggers velocity rotation and tilt QC; microcat triggers salinity derivation from conductivity, temperature, and pressure.

  4. Report rendering: the value appears as the instrument-type label in HTML reports.

Originator valid ranges

An oceansites file’s valid_min/valid_max (or valid_range) are applied only to positions: BINDEPTH, DEPTH, PRES and INSTRDEPTH outside the range are set missing. Originators use an undeclared 99999 as a fill there, and a wrong position puts data in the wrong place. Every other variable keeps its values, because an originator’s range can be wrong: ROLL with valid_min 0, or CNDC with a valid_max of 7 (an S/m bound) on values in mS/cm. A history line gives the count per variable, one line for “set missing” and one for “kept”; values kept outside the range also log a warning. oceanarray writes its own valid_min/valid_max only where a physical limit is known; the QC gross-range limits are used for flagging only.

Clock correction

Two methods are available for correcting instrument clock drift.

Two-timestamp method (recommended)

At recovery, record the GPS/computer time and the instrument’s internal clock time at the same moment. Enter both values in the YAML:

computer_clock_at_recovery: "2027-04-15T08:00:00"
instrument_clock_at_recovery: "2027-04-15T07:59:48"

Stage 2 computes drift = computer_time − instrument_time and applies a linear correction over the full deployment record (zero drift at deployment time, full drift value at recovery time).

Sign convention

Situation

Drift sign

Effect

Instrument clock was slow (behind UTC)

Positive

Stage 2 adds time to make records later

Instrument clock was fast (ahead of UTC)

Negative

Stage 2 subtracts time to make records earlier

Constant offset method

If you know a fixed offset (e.g. the clock was set incorrectly at the start) but have no recovery comparison, supply clock_offset in seconds:

clock_offset: 12    # instrument was 12 seconds slow; add 12 s to all times

Skipping clock correction

If neither clock_offset nor the two-timestamp pair is present in the YAML, no clock correction is applied. If either clock timestamp is the string unknown, the drift correction is also skipped and a warning is logged.

QC ranges

Quality control is applied in stage 3, after pressure interpolation — so instruments that receive an interpolated pressure value participate in the QC tests alongside instruments with native pressure sensors.

The gross-range test uses two nested spans. The spans define the acceptable (non-flagged) range, not the flagged range.

  • Values within suspect_span → flag 1 (pass / good data)

  • Values outside suspect_span but within fail_span → flag 3 (suspect / probably bad)

  • Values outside fail_span → flag 4 (fail / bad data)

  • NaN values → flag 9 (missing)

For example, fail_span: [-2.0, 35.0] means temperatures below −2 °C or above 35 °C are flagged 4 (bad); a temperature of 40 °C would receive flag 4.

Define thresholds under the qc_ranges key as a mapping of variable name to span pair:

qc_ranges:
  temperature:
    fail_span: [-2.0, 35.0]
    suspect_span: [-1.5, 30.0]
  salinity:
    fail_span: [0.0, 50.0]
    suspect_span: [0.0, 35.5]
  pressure:
    fail_span: [-5.0, 1050.0]
    suspect_span: [-0.5, 1020.0]
  up_velocity:
    fail_span: [-0.5, 0.5]
    suspect_span: [-0.3, 0.3]

Priority: if qc_ranges appears both at the mooring level and within an instrument clamp entry, the instrument-level values override the mooring-level values for that specific variable. Other variables not overridden at the instrument level still use the mooring-level thresholds.

Applied thresholds are stored as attributes on each *_qc variable in the stage 3 NetCDF file so that the exact configuration can be recovered from the output file alone.

HAB — height above bottom

hab (height above bottom, in metres) is the vertical distance from the seabed to the instrument’s pressure port or measurement point.

It is used for:

  • Pressure interpolation (stage 3): instruments without an integrated pressure sensor (e.g. some Aquadopp configurations) receive a pressure value interpolated from the nearest instruments that do have pressure. hab is needed to know where in the water column to interpolate.

  • Mooring diagram positioning (moordiag package): controls where the instrument icon appears on the schematic.

  • Vertical ordering in stack and grid: instruments are sorted by depth (derived from hab and waterdepth) when building the stack file.

hab is filled from hab_bottom (downward) or hab_top (upward) by the entry’s orientation when it is not given directly; oceanarray validate raises an ERROR if an instrument states an orientation but omits the matching key. If no hab can be resolved at all:

  • Stages 1 and 2 complete normally.

  • Stage 3 will skip pressure interpolation for that instrument if it has no native pressure sensor. A warning is logged identifying the instrument by serial number. The instrument will not contribute to the vertically resolved stack and grid: the stack names it in instruments_omitted (“no hab in the mooring YAML”), so a strict run (keep_going=False) stops before the grid. oceanarray validate warns about such an entry; set hab, or stack: false to keep it out of the stack on purpose.

Inline hardware and instruments

The inline list describes hardware elements attached to the mooring line but not in the clamp list: acoustic releases, floats, rope sections, shackles, and anchors. These entries are used by the moordiag diagram package; oceanarray ignores hardware-only inline entries.

An inline entry that also carries instrument, filename, and file_type fields is treated as an inline instrument — typically an ADCP mounted on a float. These are processed identically to clamp instruments.

Serial with beacon ID: when an instrument on a float carries both an instrument serial number and a float beacon ID, enter them separated by a comma:

inline:
  - serial: "16430, R01-024"
    instrument: ADCP
    filename: 16430_raw.000
    file_type: rdi-raw
    hab_bottom: 12

The first comma-separated token (16430) is used as the primary serial number for filenames and output. The remainder (R01-024) is stored as the beacon ID. oceanarray validate emits a WARNING for any inline instrument with a comma in the serial so the operator can confirm the ordering is correct.

For the HAB of an inline instrument, use hab_bottom if the instrument faces downward (transducer at the bottom of the housing) or hab_top if it faces upward.

Pending and skipped instruments

To mark an instrument as not yet available (data file not yet downloaded, instrument still at sea), use the sentinel value file_type: TBD:

- serial: "99999"
  instrument: microcat
  filename: 99999_recovery.asc
  file_type: TBD
  hab: 200

Processing is skipped for this instrument; it appears in reports as pending.

To skip an instrument that has a data file but should not be processed (e.g. it was recovered with a fault), set skip: true:

- serial: "26265"
  instrument: microcat
  filename: 26265_recovery.asc
  file_type: sbe-ascii
  hab: 380
  skip: true

Position and latitude/longitude priority

Latitude and longitude are used to compute the magnetic declination applied during Aquadopp coordinate rotation (stage 3). When multiple position fields are present, oceanarray uses the most accurate one:

  1. seabed_latitude / seabed_longitude — confirmed anchor position; highest accuracy.

  2. deployment_latitude / deployment_longitude — GPS fix from the ship at the time of deployment.

  3. planned_latitude / planned_longitude — pre-cruise planned position.

  4. latitude / longitude — generic fallback.

Only one pair needs to be provided. Coordinates should be given in degrees-decimal-minutes format, e.g. "65 29.84 N" and "009 30.12 W". The degrees component for longitude must be zero-padded to three digits (009, not 9).

Other QC blocks

The spike, flat-line and tilt tests take their own blocks, at mooring level or in an instrument entry, in the units of the variable (see Stage 3: QC flags for the defaults):

qc_spike:                  # per variable
  temperature: {suspect_threshold: 2.0, fail_threshold: 6.0}
qc_flat_line:              # per variable; counts of samples
  pressure: {suspect_n: 3, fail_n: 10, tolerance: 0.001}
tilt_qc:                   # not per variable; degrees
  suspect_threshold: 30
  fail_threshold: 50

tilt may also be given in qc_ranges as symmetric spans (suspect_span: [-20, 20]); tilt_qc takes precedence.

The blocks are checked when the description is read. These are ERRORs, so oceanarray validate reports them and processing refuses the description:

  • an unknown field (e.g. suspect_spn);

  • a span that is not two increasing numbers;

  • a threshold that is not a number of 0 or more;

  • a sample count that is not a whole number of 1 or more;

  • a block that is not a mapping;

  • a qc_ranges variable without a default and without a fail_span (an instrument entry may take the fail_span from the mooring-level block).

A variable that is not in the registry is only a WARNING (most often a typo): its thresholds apply if a file has that variable.

Calibration dips

The caldip: block names the caldip cast for each end of the deployment and the correction scheme. The correction itself is not yet applied in stage 3; the block is checked now so it can be written ahead.

caldip:
  root: ../../caldip_out      # optional; caldip_dir= wins; relative to this file's folder
  deployment: {cruise: msm142_2026, cast: castM4}
  recovery:   {cruise: odb2026, cast: castX}
  scheme: standard            # standard (default) or rapid
  # override:                 # rare: per variable, method and/or which dip to use
  #   conductivity: {method: ramp, use: pre}

  • deployment / recovery: {cruise, cast}; at least one. One dip is an ordinary case (the correction is then a constant). Each end’s file is <root>/<cruise>/<cast>_caldip.nc, or anywhere beneath the root with the cruise among the folders of its path (caldip’s proc_calib/<cruise>/cal_dip/).

  • scheme: standard or rapid (reproduces the RAPID MicroCAT processing). See Calibration — applying caldip corrections at the front of Stage 3.

  • override: keyed by temperature, conductivity or pressure; method is mean, ramp or slope (conductivity only); use is both, pre or post.

Every shape mistake is an ERROR: an unknown key or field, an end that is not {cruise, cast}, a cruise or cast that is not a single folder or file name (../x, /tmp), no end at all, an unknown scheme, method or use, a slope on temperature or pressure, or a use naming a dip the block lacks.

Validate your YAML

Before running any processing, check the YAML for missing fields and common mistakes:

oceanarray validate /path/to/proc/dsG3_1_2026/dsG3_1_2026.mooring.yaml

The validator checks that required fields are present, that instrument and file_type values are recognised, the QC blocks (Other QC blocks), the caldip block (Calibration dips), platform_code and deployment_code, and that the YAML can be parsed without errors. It also emits warnings for inline instruments with commas in the serial number so you can confirm the ordering. It exits 1 on an ERROR; add --strict to fail on warnings too.

You can validate multiple files at once:

oceanarray validate /path/to/proc/*/*.mooring.yaml

From Python

The same file is read, written and validated from Python through oceanarray.mooring:

from oceanarray import mooring

# Load one mooring's description (a path, a name + proc_dir, or a dict).
m = mooring.load("proc/dsG3_1_2026/dsG3_1_2026.mooring.yaml")
m = mooring.load("dsG3_1_2026", proc_dir="proc")

# Validate without raising (returns a list of issues).
issues = mooring.check("proc/dsG3_1_2026/dsG3_1_2026.mooring.yaml")

# Write a commented stub (what ``oceanarray init`` does).
mooring.save(mooring.template("dsG3_1_2026"), "proc/dsG3_1_2026/dsG3_1_2026.mooring.yaml")

load keeps every key exactly as written and raises MooringError on an invalid config; check never raises. name and waterdepth are required; deployment_time and recovery_time are recommended — if absent, Stage 2 uses the deployment window detected from the records.
