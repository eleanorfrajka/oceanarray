Stage 3: QC flags

Stage 3 applies QARTOD-style quality control tests to the instrument data and writes *_qc flag variables alongside each measured parameter. The tests are implemented using the ioos_qc Python package.

The flag convention follows OceanSITES (see table below).

QC flag values

Flag OceanSITES meaning QARTOD meaning Notes
1 good_data Pass All tests passed
2 probably_good_data Not evaluated Not set by oceanarray's QC — QARTOD's 2 (not evaluated) becomes 0; an originator's "probably good" word gives 2; see note below
3 potentially_correctable_bad_data Suspect Fails soft threshold; treat with caution
4 bad_data Fail Fails hard threshold; should not be used
5 value_changed — oceanarray's one extension to OceanSITES 1.4 (where 5 is unused): set only by translating an originator flag that says its QC modified the value
7 nominal_value — Not used in oceanarray (OceanSITES only)
8 interpolated_value — Pressure interpolated from HAB + neighbouring sensors
9 missing_value Missing No data; fill value

Note

oceanarray’s QC never sets flag 2. OceanSITES flag 2 means “probably_good_data” (a positive quality judgement), while QARTOD flag 2 means “test not evaluated” (no information, e.g. the spike test at a record edge or beside a gap). A QARTOD 2 is therefore written 0 (unknown), never 2. Data that pass all tests receive flag 1; data that fail the suspect threshold receive flag 3; data that fail the hard threshold receive flag 4. A 2 in an oceanarray file comes only from an originator’s flags translated by meaning (e.g. appears_probably_good), in <var>_qc_originator_mapped.

See The mooring YAML file for the qc_ranges configuration block.

Tests applied

Stage 3 applies the following tests, in order:

  1. Gross-range test: values outside [fail_span[0], fail_span[1]] are flagged 4 (bad); values outside [suspect_span[0], suspect_span[1]] are flagged 3 (suspect). Note: fail_span defines the pass range — values outside it fail.

  2. Spike test: detects single-sample spikes larger than the qc_spike thresholds: above suspect_threshold flagged 3, above fail_threshold 4.

  3. Flat-line test: flags a stuck sensor, a value that does not change by more than tolerance over suspect_n (flag 3) or fail_n (flag 4) samples (qc_flat_line; by default on pressure).

  4. Tilt QC (Aquadopp only): velocity variables are flagged when the combined pitch/roll angle exceeds a threshold. ADCP instruments use error_velocity QC instead (not a tilt test).

  5. Pressure interpolation flag: pressure values that were not measured but interpolated from neighbouring instruments are flagged 8 (interpolated).

QC is applied after pressure interpolation so that interpolated pressures also receive appropriate QC flags.

Default thresholds

The values below are the package-wide defaults from oceanarray.config.parameters (QC_GROSS_RANGE, QC_SPIKE, QC_FLAT_LINE, QC_TILT, QC_ADCP). They assume a fixed mooring in the deep ocean sampled at O(60–120 s); shallower or more energetic deployments may need tighter suspect thresholds. Any entry can be overridden per instrument in the mooring YAML — see Configuration below.

Configuration

QC ranges are configured in the qc_ranges block of the mooring YAML, at mooring level or under an instrument entry (which wins for its own variables). If absent, the package defaults are used. The spike, flat-line and tilt tests take the qc_spike, qc_flat_line and tilt_qc blocks; all four are checked when the description is read (see The mooring YAML file, “Other QC blocks”).

clamp:
  - serial: "26261"
    instrument: microcat
    ...
    qc_ranges:
      temperature:
        fail_span: [-2.0, 35.0]
        suspect_span: [-1.5, 32.0]
      salinity:
        fail_span: [20.0, 45.0]
        suspect_span: [28.0, 40.0]
      pressure:
        fail_span: [0.0, 6000.0]
        suspect_span: [0.0, 5000.0]

The fail_span defines the pass range — values outside this range are flagged 4 (fail). Similarly for suspect_span → flag 3.

See The mooring YAML file for the full qc_ranges YAML reference.

Output structure

Each QC variable has the same dimensions as its parent variable and carries these attributes:

ds["temperature_qc"].attrs == {
    "long_name": "quality flag for temperature",
    "standard_name": "sea_water_temperature status_flag",
    "flag_values": [0, 1, 2, 3, 4, 5, 7, 8, 9],  # int8, OceanSITES table 2 + 5
    "flag_meanings": "unknown good_data probably_good_data "
    "potentially_correctable_bad_data bad_data value_changed nominal_value "
    "interpolated_value missing_value",
    "conventions": "OceanSITES reference table 2",
    "qc_gross_range_fail_min": -2.5,
    "qc_gross_range_fail_max": 40.0,
    "qc_gross_range_suspect_min": -2.0,
    "qc_gross_range_suspect_max": 35.0,
    "qc_spike_suspect_threshold": 2.0,
    "qc_spike_fail_threshold": 6.0,
}

The applied thresholds are stored as attributes so the exact QC configuration can be recovered from the output file.

Note

Variable names are currently lowercase (temperature, temperature_qc). These names are subject to change in the variable renaming audit; see the warning in the oceanarray.

CLI usage

oceanarray process dsG3_1_2026 --raw-dir /data/raw --proc-dir /data/proc --stage 3

Stage 3 requires that stage 2 has already run. Run stages sequentially:

oceanarray process dsG3_1_2026 --raw-dir /data/raw --proc-dir /data/proc --stage 1 2 3

Implementation notes

  • QARTOD tests are run via from ioos_qc import qartod.

  • Multi-dimensional ADCP variables (east_velocity, north_velocity with a N_BINS dimension) are handled separately from scalar time series.

  • Tilt QC for Aquadopps uses pitch and roll recorded at each timestep.

  • All QC flags default to 9 (missing) and are only set to 1/3/4 where data are present.

Originator flags

A file that comes with its own flags (OceanSITES <CODE>_QC, or a <CODE>_flag flag variable) keeps them as written in <var>_qc_originator. Stage 3 translates them into our table by meaning, not number: the originator’s number only finds its word (flag_values paired with flag_meanings), and the word is looked up in one vocabulary, oceanarray/config/flag_meanings.yaml (e.g. appears_probably_bad → 3, modified_as_a_result_of_qc → 5). Words are matched exactly after lower-casing; a typo is listed as its own word, never guessed. A word not in the vocabulary, or one with no meaning (reserved), gives 0 (unknown) with a warning, so mask_flags never acts on a meaning we do not know. 7 and 8 are never produced from an originator word.

The translation is into the nearest severity bucket, not wording-preserving: our 3 also receives “suspect” and “probably bad” words. The originator’s words stay in originator_flag_meanings and flag_translation on the variable, and in the flag translation table of the stack and Stack cat pages.

Our flags and the translated ones are kept apart (<var>_qc and <var>_qc_originator_mapped); the stack carries both, and mask_flags hides a value when either is in the rule.

Interpolated pressure is never made from an input flagged 4 or 9 (ours or the originator’s), whatever mask_flags says: a target time whose nearest input sample is such a sample is missing (9). The inputs’ flags are recorded on the pressure in pressure_source_flags.

What QC does not do

  • It never changes a value; it only adds flags.

  • It never sets flag 2 (probably good): QARTOD’s “not evaluated” 2 becomes 0, so the OceanSITES and QARTOD meanings cannot be confused.

The thresholds used are stored on each *_qc variable.
